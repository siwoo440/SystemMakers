# 개인 채팅·파일·프로필 확장 설계

작성일: 2026-11-11. 이 문서는 1~6단계의 최초 설계와 검증 목표를 기록한다. 실제 구현 계약과 실행 조건은 [API 명세](API.md), [DB 구조](DATABASE.md), [로컬 실행](LOCAL-SETUP.md)을 기준으로 확인한다.

---
## 공통 조건

- PHP 8.3, MySQL 8.4와 기존 세션·CSRF·채널 권한 검사를 사용한다. 사용자와 메시지 ID는 기존과 같이 64비트 10진 문자열로 주고받는다.
- 변경 전에 기존 DB의 백업과 적용 상태를 확인한다. 새 스키마는 번호가 있는 보존형 마이그레이션으로 추가하고, 기존 데이터가 있는 DB에 `schema.sql`을 재실행하지 않는다. MySQL DDL의 부분 적용 가능성을 검사한다.
- 첨부 파일의 본문과 메타데이터는 사용자 선택에 따라 MySQL에 저장한다. 파일은 웹 서버에서 실행하지 않고 권한을 검증하는 다운로드 API로만 제공한다.
- 개인 채팅에서 어느 쪽이든 상대를 차단한 동안 양쪽의 새 메시지와 파일 전송을 막는다. 기존 대화는 유지하며 차단 해제 시 전송을 다시 허용한다. 서버 채널 메시지의 기존 동작은 차단 기능으로 변경하지 않는다.
- UI·API·DB 이름은 역할을 드러내는 lowerCamelCase 변수와 기존 snake_case 외부 필드로 구분한다. 코드는 Allman 스타일과 짧은 한글 명사형 주석을 따른다.

---
## 1단계: 계약과 범위

- 가입·채널·메시지·초대·세션과 WebSocket의 현재 계약을 기준으로 아래 기능을 순서대로 추가한다.
- 새 외부 API는 `backend/api/` 고정 허용 목록에만 공개하며, 기존 API와 테이블 이름·응답을 변경하지 않는다.
- 파일 크기는 초기 개발 기준 5 MiB 이하, 메시지당 파일 1개로 제한하고 추후 설정 가능하게 한다. 프로필 이미지는 별도의 크기·형식 검증을 적용한다.
- 팀 공유용 API·DB 명세는 각 구현 단계에서 실제 변경을 반영하며, 6단계 완료 후 최신 커밋을 기준으로 제작 문서를 갱신한다.

---
## 2단계: 개인 채팅 DB와 API

- 개인 대화와 그 메시지를 기존 채널의 `messages`와 구분해 저장한다. 두 사용자 ID를 정렬한 쌍에 고유 제약을 두어 같은 두 사용자 사이에 대화방이 중복 생성되지 않게 한다.
- 로그인한 사용자만 대상 사용자 검색, 대화방 생성·재사용, 대화 목록, 메시지 저장·이전·신규 조회를 사용할 수 있다. 이메일이나 비밀번호는 검색 응답에 포함하지 않는다.
- 대화 참여자 여부와 차단 상태는 저장 트랜잭션 안에서 검사한다. 메시지 순서·커서·중복 조회는 기존 채널 메시지의 문자열 ID 원칙을 따른다.
- 실제 DB 검사에서 본인과 상대방의 조회·전송, 중복 생성 경합, 본인과의 대화 거부, 제3자 접근 거부를 확인한다.

---
## 3단계: 개인 채팅 화면과 실시간

- 사용자 검색, 대화 목록, 메시지 입력·조회와 이전 대화 복구를 화면에 연결한다. 서버·채널 화면과 이동을 구분한다.
- Ratchet 구독을 개인 대화로 확장하되 연결 세션과 양쪽 참여 관계를 반복 검사한다. 알림에는 대화 본문을 넣지 않고 PHP 조회 API로 권한을 다시 검사한다.
- WebSocket 연결 손실 시 HTTP 조회로 누락을 복구하고 계정 변경·로그아웃 시 기존 화면과 구독을 정리한다.

---
## 4단계: 파일 DB와 PHP API

- 파일 본문은 BLOB 계열 열에, 원래 이름·검사한 크기·대상 메시지 정보는 별도 열에 저장한다. 작성자는 연결된 메시지에서 확인한다. 채널과 개인 대화는 각각 실제 메시지와 권한 관계를 확인한다.
- 업로드는 multipart 요청에 세션·CSRF·참여 권한과 서버 측 크기 검사를 적용한다. 서버가 생성한 ID를 사용하고 경로 또는 원본 파일명을 실행 경로로 사용하지 않는다.
- 다운로드는 현재 사용자 권한을 재검사하고 `Content-Disposition: attachment`와 `X-Content-Type-Options: nosniff`로 제공한다. 파일을 HTML·PHP로 직접 실행하거나 공개 경로에 저장하지 않는다.
- 동시 요청, 빈 파일, 최대 크기 초과, 위조된 형식, 비참여자 다운로드와 DB 실패 시 부분 저장을 검사한다.

---
## 5단계: 파일 화면 연동

- 개인·채널 대화에 파일 선택, 업로드 진행·실패 안내와 권한 확인 다운로드를 연결한다. 파일 본문은 WebSocket에 싣지 않는다.
- 성공한 파일 메시지만 표시하며, 재연결과 새로고침 후에도 파일 정보가 복원되게 한다. 실패한 전송은 사용자 확인 없이 자동 반복하지 않는다.
- MIME·확장자는 신뢰 경계로 사용하지 않는다. 모든 형식은 다운로드로 전달하고 실행 방지와 권한 검사를 공통 적용한다.

---
## 6단계: 프로필·차단·초대 링크

- 사용자명은 기존 규칙을 유지하고 상태 메시지와 프로필 사진을 추가한다. 이미지 파일은 크기와 실제 형식을 검사하고, 비실행 방식으로 제공한다.
- 차단·해제 API와 화면을 추가한다. 양쪽 개인 메시지 저장 시 차단을 검사하며 과거 메시지는 유지한다. 상대가 차단했는지 상세 사유는 노출하지 않는다.
- 현재 소유자 초대코드의 발급·폐기·만료를 유지하고 같은 출처의 공유 링크에서 코드로 참여할 수 있게 한다. 코드가 자동으로 가입되거나 로그에 남지 않도록 한다.
- 6단계 전체 통과 후 README, API·DB·실행 문서와 기존 제작 설명 문서를 실제 최신 코드와 커밋 기준으로 갱신한다.

---
## 단계별 검증과 공유

- 각 단계는 기존 기능의 회귀 검사를 포함해 검증하고, 실제 확인한 결과만 한국어 커밋 본문에 기록한 뒤 `main`에 푸시한다.
- 사용자·서버·채널·파일 권한, 동시 요청, DB 오류, 연결 중 계정 변경 및 새로고침 후 복구를 각각 검증한다.
- 로컬 `127.0.0.6`은 다른 컴퓨터에서 접속할 수 없다. HTTPS·WSS, 외부 접속과 운영 배포는 별도의 통합 단계이며 1~6단계 완료와 구분한다.
