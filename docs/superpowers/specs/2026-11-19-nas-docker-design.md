## 1. 확인한 사실과 미확인 항목

- 2026-11-19 GitHub 비교 결과 main과 기준 커밋은 모두 `8cd80ea6baaaa78bdccfcff950ba6a2e77020846`이다. 로컬 main도 같은 커밋이며 작업 시작 시 변경 파일이 없었다.
- 사용자는 NAS 보유 여부 질문에 “아직 NAS 없음”이라고 답했다. 이후 제시한 “소유하고 있는 NAS” 문장은 설명 요청에 포함된 문구이므로 장비 확보가 확인된 것으로 취급하지 않는다.
- 이후 사용자가 다른 사람의 NAS를 사용할 예정이라고 설명했으며 소유자에게 모델·Docker·네트워크·작업 허용 범위를 문의하기로 했다. 실제 사용 가능 조건은 답변 전까지 미확인이다.

- 모델 DH4300 Plus·ARM64·Docker 공식 지원을 확인했다. 실제 장비의 OS·Docker/Compose 버전과 운영 허용 범위는 확인되지 않았다.
- 공유기 모델·관리 권한·포트포워딩·통신사·공인 IP·CGNAT·이중 NAT·IPv6·도메인·DDNS도 미확인이다.
- 따라서 현재 제공할 수 있는 검증된 외부 채팅 링크는 없다. 저장소 URL은 실행 중인 채팅 사이트 주소가 아니다.
- 현재 Windows 실행 환경의 PATH에서 Node.js를 확인했다. Docker CLI는 찾지 못했으며 Docker 빌드·컨테이너 검증을 실행하지 않았다.
- 문서의 로컬 주소 `http://127.0.0.6:8088/Team006/index.html`는 이번 읽기 전용 확인에서 연결 거부였다. 현재 실행 중인 접속 링크로 안내하지 않는다.

## 2. 목표와 완료 기준

NAS에서 PHP 웹·MySQL·Ratchet을 계속 실행하고 다른 Wi-Fi 또는 이동통신망에서도 같은 HTTPS 주소로 로그인·채널 대화·개인 대화를 이용한다.

기존 계정·비밀번호 해시·서버 소속·역할·대화·첨부·프로필·친구·차단 데이터를 보존한다. 기존 인증 수명, CSRF, 계정 변경 감지, 채널·개인 대화 권한 검사를 유지한다.

컨테이너 구성 검증과 실제 NAS 배포 검증은 따로 기록한다. 실제 외부 네트워크에서 HTTPS·WSS와 권한 거절까지 확인한 뒤에만 외부 접속 완료로 표시한다.

## 3. 연결 방식 비교와 제안

| 방식 | 전제 | 장점 | 추가 조건 |
| --- | --- | --- | --- |
| Caddy 컨테이너와 직접 포트포워딩 | Docker 지원 NAS, 도메인, 외부 수신 가능 | 웹·실시간 연결을 같은 도메인으로 제공, 인증서 자동 관리 | 공유기·방화벽 설정과 인증서 발급 경로 확인 |
| NAS 내장 역방향 프록시 | 해당 NAS 기능과 WSS 지원 확인 | NAS의 기존 인증서·프록시 관리 활용 | 모델별 설정과 포트 충돌 검증 필요 |
| 외부 터널 | 직접 수신 불가, 터널 서비스 이용 가능 | CGNAT 환경에서 대안 가능 | 서비스 선정, 계정·도메인, WebSocket·전송량·접속 정책 확인 |

제조사에 종속되지 않는 Docker Compose와 Caddy 공통 구성을 먼저 준비하는 방식으로 사용자가 승인했다. 외부 터널은 CGNAT 등 직접 연결 불가가 확인될 때 별도로 설계한다.

NAS 구매·유료 서비스 가입·DNS 변경·공유기 설정은 이 문서만으로 실행하지 않는다. 장비 확보 후 모델과 운영체제의 공식 지원 자료를 확인한다.

## 4. 공통 컨테이너 구조

외부 브라우저 → 공유기 → Caddy → PHP 웹 또는 Ratchet → MySQL.

- Caddy: 외부 HTTPS 종료와 WSS 업그레이드 전달. 기존 `/Team006/` 경로를 유지하고 정확한 `/Team006/realtime`만 Ratchet으로 전달한다.
- 웹: PHP 8.3와 운영용 Apache 구성을 사용한다. PHP 내장 개발 서버는 운영 배포에 사용하지 않는다.
- 공개 문서 루트에는 진입 파일만 두고 기존 router.php의 API·정적 파일 허용 목록을 재사용한다. 저장소 전체를 Apache 정적 파일 루트로 노출하지 않는다.
- Ratchet: 웹과 같은 PHP 런타임·Composer 잠금 파일을 사용하며 독립 프로세스로 실행한다. 컨테이너 전용 실행 설정이 있을 때만 `0.0.0.0` 수신을 허용한다.
- MySQL: 기존 MySQL 8.4와 문자셋·콜레이션을 유지한다. 애플리케이션 계정과 스키마 변경 계정을 분리한다.
- 첨부: 기존 최대 5 MiB를 유지하도록 PHP의 upload_max_filesize=6M·post_max_size=7M, MySQL max_allowed_packet과 프록시 요청 제한을 함께 설정한다. 실제 최대 크기 파일의 업로드·다운로드 및 초과 거절을 검사한다.
- 공개 호스트 포트는 프록시의 HTTP·HTTPS만 대상으로 한다. DB·PHP·Ratchet 포트를 공유기나 NAS 호스트에 공개하지 않는다.
- DB와 PHP·Ratchet 연결망, 프록시와 웹·Ratchet 연결망을 구분한다. 호스트 네트워크 모드는 사용하지 않는다.
- MySQL 데이터, PHP 세션, Caddy 인증서 저장소를 각각 영속 볼륨으로 관리한다.
- 이미지 태그와 필요 시 digest를 고정하고 실제 NAS 구조에 대한 이미지 지원 여부를 검증한다. AMD64·ARM64 Linux CI는 통과했으며 실제 UGOS 환경은 별도 확인한다.
- DB 준비 확인, 서비스 상태 확인, 로그 용량 제한, 재시작 정책을 구성한다. DB 장애 후 Ratchet이 인증·알림을 정상 복구하는지도 검사한다.

위 공통 기술 선택은 설계 승인 범위이며 실제 NAS 모델·인터넷 연결 방식은 장비 확보 후 확정한다.

## 5. HTTPS·WSS와 인증 경계

- frontend/realtime.mjs는 HTTPS에서 현재 페이지와 동일한 호스트·포트의 `wss` 주소를 계산하도록 확장한다. 기존 HTTP 루프백·사설 IPv4 동작과 HTTP 공개 IP 차단은 유지한다.
- 현재 router.php의 CSP는 로컬 `ws` 주소만 명시한다. 운영 모드에서는 검증된 공개 출처의 WSS만 명시적으로 허용한다. 요청 Host 값을 검증 없이 보안 헤더에 넣지 않는다.
- Ratchet의 `REALTIME_ALLOWED_ORIGIN`에는 정확한 공개 HTTPS 출처 하나를 지정한다. 와일드카드 출처·임의 클라이언트 출처 허용으로 바꾸지 않는다.
- 운영 환경은 `APP_ENV=production`, Secure·HttpOnly·SameSite=Lax 세션 쿠키를 유지한다. TLS가 프록시에서 종료되어도 Secure 쿠키를 해제하지 않는다.
- 웹과 Ratchet은 같은 세션 볼륨·저장 경로·직렬화 형식·사용자 UID/GID를 사용한다. 양쪽에서 읽기·쓰기·세션 잠금 해제가 가능해야 한다.
- 쿠키 이름 `systemmakers_session`, 로그인 최대 12시간·유휴 30분, 로그아웃·계정 변경·권한 상실 시 차단을 유지한다.
- 현재 CSRF 헤더와 세션 토큰 비교를 보존한다. 상태 변경 요청은 기존 HTTP API를 사용하고 WebSocket은 인증된 변경 알림만 전달한다.
- 로그인·관리 요청의 제한은 REMOTE_ADDR를 사용한다. 프록시 뒤에서도 실제 접속 IP가 보존되도록 신뢰 프록시 범위를 명시한다. 임의 X-Forwarded-For를 신뢰하거나 전체 네트워크를 신뢰하지 않는다.
- AUTH_RATE_LIMIT_KEY는 충분한 난수 비밀 값으로 생성하고 재시작 시 안정적으로 유지한다. DB 비밀번호·개인 설정·백업은 Git과 이미지 빌드 문맥에서 제외한다.
- 외부 공개 전에 WebSocket 프레임·분할 메시지 누적 크기와 수신 시간을 제한한다. 현재 onMessage의 1,024바이트 검사는 완성된 메시지에만 적용되므로 별도 검증이 필요하다. 프록시의 일반 HTTP 본문 제한을 WS 프레임 제한으로 간주하지 않는다.

## 6. 기존 DB 보존과 전환

1. 원본 DB 버전과 001~005 적용 상태, 테이블·행 수·첨부 크기와 무결성을 확인한다. 원본 DB를 자동 초기화하거나 개발 seed를 적용하지 않는다.
2. 전환 중 기존 웹·Ratchet 쓰기를 멈추고 최종 논리 백업을 생성한다. 바이너리 첨부를 보존할 수 있는 hex-blob 옵션과 일관된 트랜잭션 백업을 검토하며 백업 중 DDL을 수행하지 않는다.
3. 백업 파일의 해시와 읽기 권한을 기록하고 별도 위치에 사본을 보관한다. 백업 생성만으로 복원 성공을 주장하지 않는다.
4. 새 MySQL 볼륨의 비어 있는 전용 DB에 백업을 복원한다. Windows MySQL 데이터 디렉터리를 Linux 컨테이너에 직접 연결하지 않는다.
5. 원본과 계정 ID·비밀번호 해시·소속·역할·대화 수·첨부 바이너리 해시 등을 비교한다. 누락 마이그레이션은 복원본에서 먼저 확인하고 필요한 변경만 명시적으로 실행한다.
6. 애플리케이션 계정으로 읽기·쓰기, 로그인·권한·첨부 다운로드를 검증한 뒤 접속 주소를 전환한다. 원본 DB와 백업은 검증이 끝날 때까지 보존한다.
7. 초기 NAS 전환에서는 기존 Windows 세션 파일을 무조건 복사하지 않고 재로그인을 기본 제안으로 한다. 계정·대화 데이터 보존과 세션 공유는 별개이며 NAS 내부 웹·Ratchet 세션 공유는 필수다.
8. 실패 시 신규 쓰기를 중단하고 전환 전 상태로 복귀한다. 전환 이후 신규 대화가 생긴 경우 추가 백업·차이 확인 없이 오래된 원본으로 되돌리지 않는다.

컨테이너 시작 시 schema.sql·seed·마이그레이션을 자동 실행하지 않는다. 빈 DB 준비와 기존 DB 복원을 별도 절차로 제공하고, 일반 종료 절차에 볼륨 삭제를 포함하지 않는다.

실제 이관 전에는 사용자가 보존 대상 인스턴스·DB와 백업 접근 가능 여부를 확인해야 한다. 개발 DB·검사 DB를 이름만 보고 원본으로 선택하지 않는다. 허용 중단 시간도 이관 전에 확인하며, 복원 소요 시간 측정 결과와 비교한다.

운영 백업은 일회성 이관 백업과 별도로 설계한다. 잠정 제안은 매일 암호화 논리 백업, 7일 일별·4주 주별 보관, NAS 외부 사본과 정기 복원 검사이다. 허용 가능한 데이터 손실·복구 시간과 저장 위치를 확정한 뒤 실제 주기·보관 정책을 결정한다. 백업·복원 자격 증명은 애플리케이션과 분리한다.

## 7. 장비 확보 후 확인 순서

1. NAS 본체 모델명과 관리 화면의 운영체제·CPU·메모리·저장공간을 기록한다.
2. 제조사의 해당 모델 Docker 지원과 지원 CPU 구조를 확인한다. 실제 Docker 엔진과 Compose 버전, 선택 이미지 구조를 확인한다.
3. NAS 관리 서비스의 80·443 사용 여부와 방화벽 정책을 확인한다. NAS 내부 주소는 DHCP 예약 등으로 안정적으로 유지한다.
4. 공유기 관리자 접근과 포트포워딩 가능 여부, 상위 공유기·모뎀 구성, 통신사 수신 제한을 확인한다. 공유기 WAN 주소와 외부에서 보이는 주소를 비교해 이중 NAT·CGNAT 가능성을 판단하고 필요 시 통신사에 확인한다.
5. 도메인 또는 DDNS와 A/AAAA를 확인한다. 동적 주소 변경 대응을 준비하고 도달 불가능한 IPv6 레코드를 남기지 않는다.
6. 직접 연결 방식을 택하면 필요한 외부 HTTP·HTTPS 수신 경로와 인증서 발급 조건을 검증한다. 내부 서비스나 NAS 관리 화면을 포트포워딩하지 않는다.
7. 다른 Wi-Fi와 이동통신망에서 실제 접속한다. 같은 Wi-Fi에서 공개 주소로 접속한 결과만으로 외부 연결 성공을 판단하지 않는다.

| --- | --- |
| 주소 생성 단위 테스트 | HTTPS 도메인·명시 포트·IPv6의 같은 출처 WSS, 기존 LAN WS, 잘못된 입력과 공개 HTTP 차단 |
| PHP 회귀 테스트 | 로그인·CSRF·계정 변경·채널 권한·개인 대화 권한·첨부 접근과 라우터 비공개 경로 차단 |
| 컨테이너 통합 테스트 | Compose 설정, PHP 확장·Argon2id·GD, 실제 HTTP 응답, DB 연결, 웹·Ratchet 공유 세션 |

| 장애·영속성 테스트 | WS 중단 중 HTTP 조회 유지, 서비스·DB 재시작과 재접속, 컨테이너 재생성 후 DB 보존 |
| 백업·복원 테스트 | 별도 볼륨 복원, 행 수·관계·첨부 해시·로그인 검증, 롤백 절차 |
| 실제 외부 테스트 | 유효 인증서, HTTPS 이동, Secure 쿠키, WSS 101 및 구독 승인·두 계정 알림, 다른 망에서 권한 거절 |

현재 수행한 기준 검사: `node --test tests/realtime.test.mjs tests/lan-realtime.test.mjs` 결과 7개 통과, 실패 0개. 이 결과는 현재 로컬 코드의 단위 검사이며 Docker·HTTPS·NAS 배포 성공을 의미하지 않는다.

독립 설계 검토 후 보존 대상 DB 확정·운영 백업 정책·첨부 크기 설정을 보완했다. 이 중 실제 DB와 허용 중단 시간은 배포 전 확인 사항이며 공통 Docker 구성 준비의 전제는 아니다.

구현 시 README, docs/INDEX.md, docs/REALTIME.md와 NAS 설정·검증 문서를 갱신한다. 테스트 결과는 실행 환경·성공·실패·미실행을 구분한다. 코드는 Allman 스타일과 짧은 한국어 명사형 줄 주석을 따른다. 설정 파일은 해당 파서의 필수 문법을 준수한다.

승인 후 구현·검증한 변경만 SystemMakers main에 한국어 명사형 커밋 제목과 실제 검증 결과를 담아 반영한다. 상위 HomePage 저장소는 변경하지 않는다.

## 9. 접속 링크 출력 기준

실제 도메인이 확정되면 HTTPS 웹 접속 링크와 진단용 WSS 주소를 문서·주소 출력 도구·최종 결과에 표시한다. WSS 주소는 브라우저 페이지 링크와 구분한다. 예시 도메인·미실행 주소를 실제 접속 가능한 링크로 제시하지 않는다.

현재 확인 가능한 링크는 [SystemMakers 저장소](https://github.com/siwoo440/SystemMakers)와 [기준 커밋](https://github.com/siwoo440/SystemMakers/commit/8cd80ea6baaaa78bdccfcff950ba6a2e77020846)이다.
